# scs-schema

Static schema data and manifest generator for the <a href="https://github.com/duhnunes/scs-intellisense">SCS IntelliSense</a> extension.
This repository stores one JSON file per SCS `class_name` under `data/schemas/`. CI turns them into inheritance-resolved files under `data/dist/` and a `data/manifest.json` that points at each of them through a **jsDelivr CDN URL pinned to a commit SHA**.


## Repository Purpose

This repo is a curated database describing the `class_name` blocks found in SCS unit files (`.sii`/`.sui`) of Euro Truck Simulator 2 and American Truck Simulator, together with their attributes. The content comes from the SCS modding wiki. The extension never reads `data/schemas/` directly: it reads `data/manifest.json` and fetches each class from the CDN URL listed there.


## Layout
- **`data/schemas/`**: hand-written source files. **Flat**: one file per class, named after its `class_name`, no subfolders.
  - `accessory_data` -> `data/schemas/accessory_data.json`
  - A class lists only its **own** attributes in `key`. Its direct parent goes in `superclass` (`"unit"` when there is no documented parent).
- **`data/dist/`**: generated by CI. One file per class with every inherited attribute merged in (tagged with `inheritedFrom`, plus the full `inheritsFrom` chain). This is what the extension downloads. Don't edit it.
- **`data/manifest.json`**: generated by CI. One entry per class with its CDN URL and metadata. Don't edit it.
- **`scripts/`**: the pipeline scripts (see [Scripts](#scripts)).
- **`.vscode/db.schema.json`**: JSON Schema (draft-07) describing the format of a file in `data/schemas/`.
- **`.github/workflows/`**: the CI pipeline (see [Automation](#automation)).

The field-by-field rules for writing a schema file are in <a href="./CONTRIBUTING.md">CONTRIBUTING.md</a>.

## Automation
Every pull request goes through four workflows, in order:
1. **`proxy.yml`**: PRs from forks are recreated as a branch inside this repository (keeping the original commit authorship), so the rest of the pipeline can run with write permissions. PRs opened from inside the repo skip this step.
2. **`checker.yml`**: normalizes the JSON (`scripts/formatter.mjs`) and validates it (`scripts/validate.mjs`). The PR is labeled `validated`, or `invalid-schema` with a comment listing the errors.
3. **`builder.yml`** (daily at 00:00 UTC, or manually): for each `validated` PR, bumps `meta.version` (`scripts/update.mjs`), regenerates `data/dist/` and then `data/manifest.json` (`scripts/build.mjs`), committing each step to the PR branch. The PR is labeled `ready`, or `conflict` if it conflicts with `master`.
4. **`merger.yml`**: squash-merges every `ready` PR into `master`, crediting every real commit author as a co-author.

Contributors only write files in `data/schemas/`; everything else is generated.

## How the manifest URLs work

- Each class entry in the manifest has a `url` pointing to its **flattened** file on jsDelivr:
  `https://cdn.jsdelivr.net/gh/duhnunes/scs-schema@<COMMIT_SHA>/data/dist/<class_name>.json`
  Because the URL is pinned to a commit, it is immutable: the same URL always returns the same content.
- The build runs in two phases so that the pinned commit really contains the file: `data/dist/` is generated and committed first, and only then is the manifest written against that commit's SHA.
- An entry's `url` is only rewritten when the file's hash changed; unchanged classes keep their old URL.
- Besides `url`, each entry stores `name`, `description`, `hash` (`sha256:` prefix, computed over the `data/dist/` file), `size`, `metaVersion`, `superclass` (`null` when it is `"unit"`) and `documentationStatus`. The manifest itself also has `formatVersion` and `generatedAt`.

## Scripts

> [!NOTE]
> `update.mjs` and `build.mjs` are meant to run in CI, not locally: the manifest URLs need the real commit SHA produced by the pipeline.
> `validate.mjs` and `formatter.mjs` are safe to run locally (`pnpm validate`, `pnpm format:schemas`).

- `scripts/update.mjs`: bumps `meta.version` in `data/schemas/` based on the Conventional Commits that touched each file since the last `ci(update):` commit (`BREAKING CHANGE`/`!:` -> major, `feat` -> minor, anything else -> patch). Never touches `data/dist/` or the manifest.
- `scripts/build.mjs`: resolves inheritance (`scripts/lib/inheritance.mjs`). `--dist-only` writes `data/dist/`; `--manifest-only <ref>` writes `data/manifest.json` against that commit. With no flag it runs both (local preview only).
- `scripts/validate.mjs`: checks every file against `.vscode/db.schema.json` (Ajv), plus cross-file rules: `scope` equals the file name, `superclass` exists, no inheritance cycle, no duplicate `scope`.
- `scripts/formatter.mjs`: normalizes field order and arrays. It never adds missing fields, so omissions are still caught by validation.
- `scripts/log.mjs`: console summaries used by the scripts above.

## Contributing

Contributions are welcome!
To add or edit schema files, please read <a href="./CONTRIBUTING.md">CONTRIBUTING</a> first.
It has the exact rules for file naming, the JSON structure of each schema file and how to decide what to fill in from the wiki.

## Notes for integrators

- The manifest is designed to be consumed by the SCS IntelliSense extension and also by any external tooling that needs stable, CDN-hosted class data.
- Fetch the `url` of each entry (the flattened file), not `data/schemas/`: source files don't include inherited attributes.
- Use `hash` and `size` to verify integrity. Because URLs are tied to a commit SHA, the same URL always resolves to the same content.
